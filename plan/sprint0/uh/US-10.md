[G06-HU10] — Control de frescura de los datos y avisos

> **Épica:** EP-04 · Contratos de Lectura e Ingesta
> **En simple:** el sistema avisa cuando un tema lleva demasiado tiempo sin enviar datos, para no mostrar información vieja en el panel.

Descripción (Como / Quiero / Para)
Como: ADMIN
Quiero: saber si los datos del panel están al día y que avise cuando un tema deja de enviarlos por más de 15 minutos
Para: no mostrar información desactualizada y poder reaccionar a tiempo

Notas / Observaciones
Reglas de negocio:
- Los reportes se consideran al día si el último dato recibido tiene menos de 15 minutos.
- Si un tema supera los 15 minutos sin enviar datos, se marca como desactualizado y se avisa.
- Cuando el tema vuelve a enviar datos, el aviso se quita solo.
- El panel muestra una insignia en los reportes afectados.
Validaciones:
- El horario operativo define cuándo se controla la frescura.
Datos obligatorios: último timestamp por tema, umbral (15 minutos).
Performance: el control corre cada 2 minutos sin afectar a los usuarios.
Seguridad: no aplica (interno).
Accesibilidad: la insignia se muestra con texto claro.
Otros: el aviso se envía al sistema de notificaciones.

Criterios de Aceptación (CA)
CA1: Si un tema lleva más de 15 minutos sin enviar datos, el sistema avisa y marca los reportes.
CA2: La API expone el estado de frescura (isStale) para que la UI muestre la insignia.
CA3: Al volver los datos, el aviso se retira automáticamente.
Extras (opcional): —

BDD (mínimo 3 escenarios)
Característica: Control de frescura de datos

Escenario 1: Datos desactualizados
Dado: que un tema lleva 22 minutos sin enviar datos
Cuando: se revisa la frescura
Entonces: se avisa que los reportes pueden estar desactualizados y se marca el estado

Escenario 2: Datos al día
Dado: que todos los temas enviaron datos en los últimos 15 minutos
Cuando: se revisa la frescura
Entonces: los reportes se muestran como al día, sin avisos

Escenario 3: Normalización
Dado: un reporte marcado como desactualizado
Cuando: el tema vuelve a enviar datos
Entonces: el aviso se retira en el próximo refresco

Prototipo
Mock API / Swagger:
- GET /api/reports/health/freshness → estado de frescura por tema

Estimación / Prioridad
Puntos (Fibonacci): 3
Prioridad (MoSCoW / Numérica): Must

Dependencias / Impactos
Servicios involucrados: reporting-service, Kafka
Módulos afectados: monitor de frescura, alertas
Otros equipos / aprobaciones: T11 (notificaciones)
Impacto en datos / migraciones: tabla de estado de contratos
Riesgos y mitigación (opcional): depende de la ingesta (US-08)

Tareas asociadas (para Taiga)

3. Emitir el aviso y marcar los reportes afectados.
4. Quitar el aviso cuando el tema normaliza.
5. Exponer el estado de frescura por API.
6. (Front) Insignia de datos desactualizados en el panel.
7. Documentar, actualizar el sdd y cargar la tarea en Taiga.
